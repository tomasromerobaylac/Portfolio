Case study · ParkAppCaso · ParkApp

Two drivers, one parking spot, the same millisecond. Dos conductores, un lugar, el mismo milisegundo.

While building a parking reservation system I found a race condition that let two users book the same spot. This is how I approach bugs: reproduce, isolate, then fix it where it can't come back. Construyendo un sistema de reservas de estacionamiento encontré una condición de carrera que permitía que dos usuarios reservaran el mismo lugar. Así encaro los bugs: reproducir, aislar y corregir donde no pueda volver.

  1. ReproduceReproducir

    Two concurrent reservations on the same spot both succeed. The code checks availability first and writes after.Dos reservas simultáneas sobre el mismo lugar terminan ambas bien. El código primero consulta disponibilidad y después escribe.

  2. IsolateAislar

    Classic check-then-act: between the SELECT and the UPDATE, another request can take the spot.Un check-then-act clásico: entre el SELECT y el UPDATE, otro pedido puede quedarse con el lugar.

  3. Fix at the sourceCorregir en el origen

    A conditional UPDATE inside one transaction, using the affected-row count as optimistic concurrency control. The database enforces the rule, not the UI.Un UPDATE condicional dentro de una sola transacción, usando la cantidad de filas afectadas como control de concurrencia optimista. La regla la garantiza la base, no la interfaz.

SQLreservas.sql — parkapp
reservas.sqldatabase.py
-- before: check, then act race
SELECT ocupado FROM lugares
 WHERE id = 'B-12' AND id_cochera = 4;
-- …another request lands here…
UPDATE lugares SET ocupado = 1
 WHERE id = 'B-12' AND id_cochera = 4;

-- after: one atomic, conditional write safe
BEGIN;
UPDATE lugares SET ocupado = 1
 WHERE id = 'B-12' AND id_cochera = 4
   AND ocupado = 0;
-- rowcount = 1 → reserved · 0 → already taken
COMMIT;
